# 技术方案生成提示词（Prompt）

> **用途**：可复现地生成 `docs/技术方案.md` 及其 Word 版本。把下方「主提示词」整段投给模型，并附上「输入材料」中列出的文件即可。
> **适用范围**：FDE 训练「方案设计」阶段（需求 → 端边云图、Ontology、BOM/SDK 及契约 → 指导分工与构建）。
> **配套文件**：`技术方案.md`、`技术方案.docx`。

---

## 一、输入材料（喂给模型的文件清单）

| 顺序 | 文件 | 作用 |
| --- | --- | --- |
| 1 | `交房缺陷与整改协同-现场调研报告.md` | 任务 1–3 作答、标准参考答案、评分与改进建议 |
| 2 | `discovery-report(2).md` | 业务需求发现报告：需求假设、证据台账、访谈记录 |
| 3 | `现状流程图.md` | 六角色泳道主流程、四类异常路径、瓶颈责任标注 |
| 4 | `客户简报(1).html` | 客户原始诉求、项目目标与范围、边界 |
| 5 | `现状信息请求表(1).html` | 待索取资料清单与核对指标 |
| 6 | `业务发现访谈问题库(1).html` | 六角色访谈切点，用于核对事实编号归属 |
| 7 | `利益相关者资料与分工(1).html` | 角色职责与协作边界 |
| 8 | `discovery-report.json` / `.csv` | 结构化事实编号，用于校验引用 |

> 事实编号体系为 f00–f55，来自六角色访谈（顾明岚、林亦舟、唐映秋、秦芮、傅景、叶书）。

## 二、主提示词（可直接复制使用）

```text
你是 FDE（Forward Deployed Engineer）训练项目的方案设计负责人。
请基于我提供的【输入材料】，为「城居发展 · 交房缺陷与整改协同」项目撰写一份技术方案，
作为「方案设计」阶段的交付物（试点方案与构建计划）。

【任务目标】
把需求定义阶段的结论，转成可指导分工与构建的技术设计：
端—边—云架构图、业务 Ontology、BOM/SDK 与接口契约，以及代理职责、试点计划与终止标准。

【必须包含的板块，按序输出】
一、需求基线与约束（方案设计的输入）
    1.1 业务目标与验收硬指标（表格）
    1.2 待验证的问题聚焦（不超过 3 项，说明为何优先）
    1.3 不可越过的权限与口径红线
    1.4 试点前必须补齐的口径（阻断项，表格带责任人与事实编号）
二、最小试点与排除范围（范围内 / 明确不做，表格）
三、业务价值及对照测量（基线、目标、测量口径、对照方式）
四、端—边—云架构（Mermaid flowchart + 分层职责说明表）
五、Ontology（业务对象与关键字段表 + Mermaid erDiagram）
六、BOM / SDK 与技术契约
    6.1 组件清单 BOM（组件、形态、职责、状态）
    6.2 接口契约（读写权限、字段、频率、中断降级、歧义处理、写回）
    6.3 关键 SDK / 集成点
七、代理职责与人工控制（模块可做 / 只能由人完成 / 责任人）
八、构建计划与责任人（阶段、任务、输入、输出、责任人、前置条件）
九、成功、继续与终止标准（关卡、标准、判定签核、未达标动作）
十、风险、留存与合规
附：事实编号索引说明

【硬性约束】
1. 数据来自合成训练场景，所有结论必须表述为「待验证假设」，不得写成已确认需求或已验证结果。
2. 每条业务事实必须标注证据编号（f00–f55）；未标注的陈述一律删除或改写为待核实项。
3. 明确区分「角色自述的访谈事实」与「可核验证据」，不得把 36 条访谈覆盖等同于需求已确认。
4. 试点边界：单楼栋、历史资料回放 + 小范围并行；只读汇总优先，不替换现有业务、不回写工单、不自动关单。
5. 权限红线不得突破：专业签核、质量责任与赔偿、客户签字、对外承诺只能由授权人员完成；
   缺陷归类与整改追踪不代替工程质量鉴定或客户签字；业主意见不可被自动覆盖。
6. 98% 是「缺陷定位准确率」，不是「缺陷归类正确率」；其判定人、样本量、统计口径尚未核实，
   必须作为阻断项列出，不得在方案里自行设定口径。
7. 「完成」定义存在冲突（施工＝整改结束，客户＝复验通过），须列为待统一口径，不得替业务方拍板。
8. 指标须固定分母、排除规则与统计周期；一条缺陷拆多张工单会导致复验通过率重复计数，须给出去重方案。
9. 接口约束：三套系统账号独立、无统一状态视图；接口只读、不自动确认交付或关闭争议工单；
   接口中断时使用带时间戳只读快照并标注「暂未更新」。
10. 异常四类触发（未复验关单、资料缺依据、两版本冲突、关键系统不可用）须统一转人工，
    并标注触发原因、接手人、确认时间；错误结果不得覆盖原记录。
11. 审计留痕六要素：业务编号、资料版本、事实引用、建议结果、人工改动、签核人；
    不记录口令与不必要个人信息；评价记录暂留 90 天且删除执行人未定，须列为待补。
12. 合成训练不代表真实授权、业务执行或客户验收。

【表达要求】
- 面向项目组与业务负责人，措辞专业、克制，不使用「评委」「打分」「交作业」等内部用语，不写更新日志式段落。
- 能用表格说清的优先用表格；架构与对象关系用 Mermaid 代码块（GitHub 可直接渲染）。
- 不虚构任何已验证数据、系统能力、接口字段或审批结论；不确定的一律标注「待核实 / 待确认」并写明由哪个角色补齐。
- 不与现有资料矛盾；如发现材料之间口径冲突，保留分歧并列入待补清单，不要自行合并或选择宽松条款。

【输出格式】
输出单份 Markdown 文档，标题为「城居发展 · 交房缺陷与整改协同 —— 技术方案」，
开头用引用块写明：文档性质、数据基础、试点边界、前序依据。
板块标题用「一、二、三……」，子节用「1.1 / 1.2」；表格使用标准 Markdown 表格。
不要输出思考过程、不要输出与本方案无关的说明、不要在文末附加寒暄。
```

## 三、自检清单（生成后逐条核对）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | 板块完整性 | 十个板块 + 附录齐全，顺序一致 |
| 2 | 证据编号 | 每条业务事实均可追溯到 f00–f55 |
| 3 | 假设标记 | 无「已确认」「已验证」等结论性表述 |
| 4 | 98% 口径 | 明确写为定位准确率，且判定人/样本量列为待补 |
| 5 | 完成定义 | 保留双方分歧，未替业务方拍板 |
| 6 | 只读边界 | 全篇无自动关单、自动赔偿、写回工单的设计 |
| 7 | 人工控制 | 五类只能由人完成的判断均已列明并指定责任人 |
| 8 | 异常路径 | 四类触发齐全，含触发原因/接手人/确认时间三字段 |
| 9 | 去重方案 | 主编号去重、固定分母、排除规则均已说明 |
| 10 | 终止标准 | 有具名签核人与未达标动作，非泛泛而谈 |
| 11 | 审计合规 | 六要素齐全，含 90 天留存待补说明 |
| 12 | Mermaid 可渲染 | flowchart 与 erDiagram 语法正确，节点文字用引号包裹 |

## 四、复现与迭代方式

1. 将「输入材料」8 项文件按表中顺序作为附件或上下文提供给模型。
2. 粘贴「主提示词」整段，要求输出 `.md` 文件。
3. 用「自检清单」逐条核对；未通过的项目追加一句修正指令重跑，例如：
   `第 4 项未通过：请把 98% 统一改为「缺陷定位准确率」，并把判定人与样本口径移入 1.4 阻断项。`
4. 定稿的 `.md` 转成 `.docx`（保持板块与表格一致），两版一并归档到 `docs/`。
5. 若老师更新了板块要求，只修改「必须包含的板块」一节并重跑，不要整体重写正文，避免丢失已核对过的证据编号。

## 五、配套说明

- 本提示词与 `技术方案.md` 为同一轮产出，提示词中的板块清单即文档目录；两者如有不一致，以老师最新要求为准。
- `harness`（评估运行环境）已在本机部署，本提示词不生成 harness 配置，仅在技术方案第六、九章引用其评估用例与关卡。
- 模型输出仅作为方案草稿，所有业务口径与审批结论仍须由具名角色确认后方可进入试点。
